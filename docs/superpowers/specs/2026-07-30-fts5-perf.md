# FTS5 performance follow-ups

**Date:** 2026-07-30
**Branch:** `feat/fts5-search` (continuation)
**Status:** Draft — supersedes nothing

## Goal

Apply two concrete recommendations from the 2026-07-30 performance
review of the FTS5 search subsystem:

1. **Weighted BM25** — replace the default `bm25(tdoc_search)`
   call (all columns equal-weighted at 1.0) with a configurable
   column-weight vector so the identifier-first / title-heavy
   workload ranks correctly.
2. **Composite indexes on filter columns** — add indexes that
   match the search query's filter-push-down shape so the SQL
   planner can prune rows cheaply.

Both changes are scoped tightly. The v1 design (per the original
spec) already covers everything else the reviewer flagged —
`SearchQueryBuilder` runs `normalize_query` per-token, the
single-integration `upsert_for_tdoc` hook keeps the index in
sync, the resumable / `--stale-only` rebuild keeps large corpora
manageable, and the `EmbeddingReranker` hook is the escape hatch
for multi-million-document scale.

## Non-goals

* **No `bm25s` external library.** Native FTS5 BM25 is the right
  tool for the documented v1 scale (low-mid hundreds of thousands
  of documents).
* **No contentless / external-content FTS5 schema.** Deferred
  until rebuild-time measurement proves a bottleneck.
* **No micro-benchmark test infrastructure.** Reviewer's checklist
  item #6 — adding benchmark plumbing is a project on its own and
  out of scope here.
* **No slow-query logging.** Reviewer's checklist item #7 —
  useful at multi-million-document scale, premature at v1.
* **No full re-architecture of `_build_index_text`.** Reviewer's
  checklist item #3 — the current single-transaction
  `engine.begin()` upsert is fine at v1 scale.

## Design

### 1. Weighted BM25

Add two new fields to `Settings.search`:

```python
bm25_weights: tuple[float, ...] = Field(
    default=(
        10.0,   # title
        1.0,    # ftp_url
        0.5,    # meeting_title
        0.5,    # meeting_location
        2.0,    # wis
        4.0,    # cover_text
        3.0,    # change_text
        3.0,    # ttcn_text
    ),
)

snippet_column: Literal[
    "title",
    "ftp_url",
    "meeting_title",
    "meeting_location",
    "wis",
    "cover_text",
    "change_text",
    "ttcn_text",
] = Field(default="title")
```

Defaults match the reviewer's relative-weight guidance:

| Column            | Weight | Rationale                          |
| ----------------- | -----: | ---------------------------------- |
| `title`           |   10.0 | Highest signal — what users read   |
| `cover_text`      |    4.0 | Structured CR summary              |
| `change_text`     |    3.0 | Core technical content             |
| `ttcn_text`       |    3.0 | TTCN-specific signals              |
| `wis`             |    2.0 | Work-Item searches                 |
| `ftp_url`         |    1.0 | Almost never useful for ranking    |
| `meeting_title`   |    0.5 | Context only                       |
| `meeting_location`|    0.5 | Context only                       |

The FTS5 virtual table has 8 indexed columns (1 `UNINDEXED`
`tdoc_id` + 8 indexed), so 8 weights is correct. Pydantic
validates the tuple length at construction.

### 2. Repository changes

`SQLAlchemySearchIndexRepository.search()` switches from:

```sql
SELECT ..., bm25(tdoc_search) AS score,
       snippet(tdoc_search, 1, '<<', '>>', '…', 8) AS preview,
       ...
ORDER BY score
LIMIT :limit
```

to (with weights `[w0..w7]`):

```sql
SELECT ..., bm25(tdoc_search, w0, w1, ..., w7) AS score,
       snippet(tdoc_search, :col_idx, '<<', '>>', '…', :tok) AS preview,
       ...
ORDER BY bm25(tdoc_search, w0, w1, ..., w7)
LIMIT :limit
```

The `:col_idx` is the 0-based positional index of
`Settings.search.snippet_column` in the column list
(`title=1` is the FTS5 1-based column index because FTS5's
`snippet()` uses 1-based, and `tdoc_id` is column 0 = `UNINDEXED`
but still counted).

The repo resolves `bm25_weights` and `snippet_column` from
`get_settings()` at construction time and caches them on
`self._weights` / `self._snippet_column`. (Settings read at
construction is acceptable; the existing code already reads
`Settings.search.auto_index_on_parse` the same way in
`TDocCrService._index_after_parse`.)

### 3. `--explain` wire-up

The T10 flag `--explain` was declared but never wired
(see T10 review follow-up). Implement it now: when
`--explain` is set, the CLI prints the resolved MATCH
expression plus the BM25 weight vector + snippet column
to stderr before the result table.

Output format:

```
# search config
match:           "NB-IoT"
snippet_column:  title (col 1)
snippet_tokens:  8
bm25_weights:    [10.0, 1.0, 0.5, 0.5, 2.0, 4.0, 3.0, 3.0]
```

### 4. Composite indexes

Add two composite indexes via `_create_search_schema()`
(matching the existing FTS5 + meta sidecar pattern):

```sql
CREATE INDEX IF NOT EXISTS idx_tdocs_release_spec
    ON tdocs (release, spec);

CREATE INDEX IF NOT EXISTS idx_tdocs_uploaded_date
    ON tdocs (uploaded_date);

CREATE INDEX IF NOT EXISTS idx_meetings_name_tsg
    ON meetings (name, tsg);
```

Rationale:

* `tdocs(release, spec)` — covers `--release` + `--spec`
  filters (the two most common compound filter combos).
* `tdocs(uploaded_date)` — covers `--since` / `--until`
  range scans.
* `meetings(name, tsg)` — covers `--meeting` + `--tsg`
  filter combos; matches the existing convention of
  indexing columns used in CLI filters.

The existing `tdocs.meeting_id` index and `meetings.tsg`
index cover the remaining cases.

`IF NOT EXISTS` makes the DDL idempotent for re-runs of
`create_schema()` (matching the existing FTS5 / meta
sidecar pattern).

  `bm25_weights` length validation + `snippet_column`
  Literal values.
* `tests/integration/test_search_weighted_bm25.py` — index
  10 rows, run a query, assert that a hit on `title`
  ranks higher than a hit on `meeting_title` only
  (proves the weights are wired, not just present in SQL).
* `tests/integration/test_search_indexes.py` — smoke:
  `create_schema()` creates the indexes; verify via

  `test_search_help_lists_filters` to keep working; add

## Open implementation notes

* Settings caching — the new fields are read once in
  `SQLAlchemySearchIndexRepository.__init__`; live updates
  to `bm25_weights` require a service restart. Acceptable
  for v1 (operators restart the CLI after editing TOML).
* Snippet column index — FTS5 `snippet()` uses 1-based
  column indices where `tdoc_id` = 1 (it's UNINDEXED but
  still numbered), `title` = 2, `ftp_url` = 3, etc. The
  repo derives the index from the column name via a
  constant tuple; the test pins the mapping.
* Reviewer's #6 (explicit `ORDER BY bm25(...)`) — adopted
  in the repo.

## TL;DR

Two scoped performance tweaks: weighted BM25 (title ≫ body)
+ three composite indexes on filter columns. No schema
migrations (alembic isn't wired) — the indexes ride along
on `_create_search_schema()` like the FTS5 virtual table.
